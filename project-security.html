Multi-Camera Threat Detection

A real-time system watching several camera feeds at once for weapons, falls and violence, with automatic evidence capture and escalation. I was the sole engineer: model training, architecture, and the entire runtime including the threading model, alerting and dashboard.

What it does

In a school, a false alarm and a miss are both unacceptable, and they pull the design in opposite directions.

Per-camera detector assignmentEach camera configured independently in JSON, so an entrance camera can run weapon detection only while a corridor camera runs fall detection only.
Two-stage weapon detectionA fine-tuned detector proposes regions, then CLIP verifies each crop against positive and negative text prompts before anything counts as a threat.
Falls from geometryDerived from person bounding-box proportions, required to persist across consecutive frames before firing.
Violence from temporal sequencesA 3D-CNN over a rolling 16-frame buffer, rather than judging single frames.
Automatic evidence escalationA frame or reconstructed MP4 clip uploaded to a category-specific cloud folder, made link-accessible, and emailed to security staff with the link embedded.
Live operator dashboardMJPEG feeds with an on-frame HUD, a real-time violence-score meter, and a health panel marking each camera online or offline with FPS and queue depth.

Problems I solved

Two problems worth describing: one architectural, one that only the logs revealed.

A detector for recall, CLIP for precision

Problem

A detector tuned for high recall on weapons fires on phones, pens and wallets — dark, hand-held, roughly rectangular objects in the same size range. Tuned for precision instead, it misses real weapons. Both failure modes are unacceptable in a school: false alarms destroy trust and get the system switched off; misses defeat the purpose.

Design

Separate the two concerns. The detector runs at a deliberately permissive 0.40 confidence threshold, optimising for recall. Every proposed crop then goes to CLIP, scored against a prompt set containing both positive classes (weapon, gun, pistol, rifle, knife) and explicit negative classes (mobile phone, pen, eyeglasses, wallet). A detection is promoted only if the top-scoring prompt is positive.

Why the negatives matter

CLIP is being used as a discriminative classifier, not a similarity scorer. Adding the exact confusable objects as competing labels means a phone is not merely "less similar to a weapon" — it is actively assigned to a phone label that outranks the weapon labels. Without negatives, a softmax over positive prompts alone would confidently label a phone as whichever weapon it most resembled.

Bonus property

The detector can be retrained without retraining a classifier, and the confusable-object list extends by editing a list of strings. Adding "a water bottle" is a one-line change.

The incident log revealed an alerting problem, not a detection problem

What the logs showed

Reviewing incident timestamps showed the same event generating repeated alerts rather than one.

Diagnosis

Detection was working correctly. The alerting policy was wrong: without a cooldown keyed to the incident rather than the frame, a sustained threat in view produces an alert per detection cycle.

Why it matters

An operator who receives twelve alerts for one event learns to ignore alerts. The failure was in how the system communicated, not in what it saw.

What I am not claiming

All 7 commits landed on a single day as a publication of pre-existing work, so commit history is not a record of development time and I state no duration for this project.

The repository README claims a "under 1 second" weapon response time. The measured average latency of 698 ms supports it, but the same run recorded per-camera throughput as low as 0.5 FPS, so the claim holds on average rather than in every condition.

Latency was measured on CPU. I have not benchmarked it on a GPU deployment.
