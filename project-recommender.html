Movie Recommender from Scratch

A matrix factorization recommender with no recommender library in it. I derived the update equations from the log joint, wrote them in NumPy, compiled the inner loops with Numba, and trained on all 32 million MovieLens ratings. The point was to understand the method instead of calling it.

What it does

You search for films, rate a few, and get recommendations. Behind that, three models stacked so each one fixes what the last one misses.

Learns taste as two sets of vectorsEvery user and every movie gets a short vector. Their inner product is the predicted taste match, and alternating between solving for users and for movies is the whole training loop.
Separates generosity from qualityTwo bias terms absorb the fact that some people rate everything highly and some films are simply better. Without them the factor model wastes its capacity relearning both.
Gives unrated films a starting pointA movie with no ratings has no signal, so its vector is pulled toward a mean predicted from its genres instead of toward zero. The genre vectors are learned too.
Fits one new user without retrainingThe movie vectors are frozen and exported. Adding your ratings solves a single small system for your vector only, which is why the app answers immediately.

Problems I solved

The useful results here were mostly the ones that contradicted what I expected going in.

Compiling beat parallelizing, which I had backwards

Problem

One user-side update over 64,301 ratings took 0.81 s in plain NumPy. At 200,948 users per sweep and 20 sweeps, that is not a training run anyone waits for.

Assumption

Each user solves independently, so I expected this to be embarrassingly parallel and to scale with thread count.

Result

Numba compilation alone took it to 0.0148 s — a 55× speedup. Adding threads made it marginally slower, at 0.0153 s.

Why

The per-user work is a 10×10 solve. It is real parallelism, but each task is far too small to pay back the scheduling overhead. Compilation had already removed the actual bottleneck, which was Python loop dispatch.

Two cold-start experiments disagreed, and the pessimistic one was right

Controlled test

I held out every rating for 1,063 movies. The genre prior improved them: RMSE 0.989 → 0.967. A clean win for the idea.

Natural test

On the films that were genuinely unrated in the split, the same prior made things slightly worse: 1.031 → 1.045.

Reading

Naturally-unrated films are not a random sample. They are obscure, and genre is a weaker guide for an obscure film than for a popular one that merely happened to be held out. My controlled experiment had quietly built in the assumption it was meant to test.

Decision

I reported both, and said in the paper that the observational result is the one that reflects deployment. It would have been easy to publish only the first table.

More capacity did nothing, and the regularizer did everything

Result

Doubling the factors from K=10 to K=20 moved test RMSE by 0.001 (0.7785 → 0.7777) for 2.2× the training time, while train RMSE fell much further, 0.712 → 0.663.

Reading

The extra capacity went into memorising the training set. Meanwhile the prior strength mattered a lot: a weak setting gave 0.786 and a strong one 0.801, against 0.778 at the value I kept.

What deriving it taught me

Writing the normal equations by hand made clear that the effective penalties are the ratios τ/λ and τb/λ. So changing λ alone silently moves both — easy to miss when a library exposes them as three independent knobs.

A logging bug I wrote up instead of quietly fixing

Problem

The bias training run logged 8 updates, then restarted its counter and logged 20 more. The learning curve was wrong and so was the update count in my notes.

Fix

I refit the bias model independently to confirm all 28 updates really happened, corrected only the axis, and left the factor models at their genuine 20 sweeps.

Decision

It became a labelled subsection of the paper rather than a silent re-plot. A corrected figure with no explanation is indistinguishable from one that was always right.

Engineering details that mattered

Mixed precision by roleRatings in float32 to halve the memory of the one huge array; parameters and error accumulators in float64, because summing millions of residuals in float32 loses accuracy exactly where it counts.
Never allocate the full prediction matrixEvaluation is batched. A ratings-by-factors matrix at this scale does not fit, so the naive vectorised version is not an option.
Solve, don't invertThe regularizer keeps the normal matrix positive definite, so each update is a direct solve. Forming an explicit inverse would be slower and less stable.
Reproducible by recordSeed 42 throughout, plus a run manifest capturing library versions, platform, and SHA-256 hashes of both input CSVs.

What I am not claiming

This is coursework for Prof. Ulrich Paquet's course at AIMS, written up in the ICML template as a draft. It is not a peer-reviewed publication.

There is no validation set. Hyperparameters were chosen while test RMSE was being monitored, so the test set is not an untouched holdout and 0.78 is mildly optimistic as an estimate on genuinely new data. The paper states this in the evaluation protocol rather than burying it. The fix is a three-way split, selecting on validation only.

Cold users were never tested. The natural split happened to leave zero cold users, so that row of the results table is empty. A brand-new user still needs ratings or a fallback.

RMSE measures rating prediction, not recommendation quality. Nobody sees a predicted rating — they see a ranked list, and a model can improve one while leaving the other unchanged.
