Property-Sales AI Assistant

A conversational sales assistant for a large mixed-use development. Buyers ask in Arabic, English or another language, by text or voice, and get answers grounded in an approved knowledge base together with the relevant floor plans and renders.

What it does

A sales assistant is judged on what it refuses to say as much as what it says. An invented price is a commercial problem, not a technical one.

Shows the right picturesFloor plans, renders and specification sheets retrieved alongside the text, scoped to the building or unit type under discussion, with images already shown earlier suppressed.
Numeric filtering in natural language"under 90 m²", "between 70 and 100", "أكبر من 120 متر", plus qualitative forms like "big" or "compact" — including Arabic-Indic numerals.
Understands follow-ups"What about the ground floor?" or a bare "yes" resolve against remembered state: last building discussed, last catalogue shown, last question asked.
Speaks the buyer's languageEnglish, Egyptian dialect, or whatever they write in — with knowledge-base text rewritten into the reply language rather than pasted verbatim.
Refuses out of scopeCompetitor questions get a fixed redirect. Unknown building codes get "I don't have that, here is the official channel" rather than an invented answer.
Captures leadsAnd powers a sales analytics dashboard with eight endpoints: overview, timeseries, intents, properties, funnel, queries, leads and behaviour.

Problems I solved

Four problems where the fix depended on understanding exactly why the obvious approach fails.

A grounding guard that fails closed on exactly one category

Problem

The obvious anti-hallucination guard checks every claim against the retrieved context and blocks anything unsupported. In practice that blocks a large fraction of good answers, because natural sales phrasing legitimately rephrases and connects facts.

Decision

The guard intercepts only explicit financial claims — prices, down payments, instalments, currency amounts, "sold out", and their Arabic equivalents. If the answer contains one of those and the retrieved context does not, the answer is blocked. Everything else passes.

Reasoning

A risk asymmetry specific to the domain. A slightly loose description of a garden is recoverable in the next message. An invented price is a commercial liability. Asymmetric risk deserves an asymmetric guard.

Conversational state that resolves a bare "yes"

Problem

A buyer answering "yes" to "would you like to see the floor plans?" is sending a message with no content of its own. Resolving it requires knowing what was asked.

Design

The system keeps compact session state — last building code, last catalogue shown, seen image URLs, last assistant question — and rewrites confirmations into self-contained queries.

The ordering bug

The rewrite must happen before the cache key is computed. Otherwise the key is built from the bare "yes", the image search runs on the wrong query, and a cache hit returns images for whatever the last person who said "yes" was asking about. Three distinct consequences, all from ordering one operation correctly.

Carve-outs

Building context is injected into follow-up image queries, with three exceptions, each of which was a real bug: project-wide topics must not be scoped to the last building; an explicit zone reference is self-contained; and a catalogue switch is project-wide. Each is the memory feature working exactly as designed and producing a wrong answer.

An LLM bias, cross-checked with a cheap deterministic tool

Observation

The query analyzer has a measurable bias: when it classifies a query as out of scope, it tends to report the language as English even when the query is plainly in another language. A French question came back as language: en. The consequence is a refusal delivered in the wrong language, which reads as broken.

Fix

Run langdetect on the raw text as a cross-check — but only when the analyzer said "en" specifically, because that is the only direction the bias has actually been observed in. If langdetect disagrees and returns a valid code, it overrides. If it throws, the analyzer stands.

Principle

Rather than replacing the LLM with a heuristic or trusting it blindly, use a cheap deterministic tool to check the one failure mode you have actually seen, and scope the override to that direction only.

A string bug that only corrupts Arabic

Symptom

Extracting the topic from an image request produced corrupted Arabic words.

Cause

The code used str.strip(chars), which strips individual characters, not words. Given leading Arabic filler, it stripped those letters from both edges — including from the middle of legitimate adjacent words.

Why Arabic

In English this bug is often invisible, because the stripped characters rarely begin the next real word. In Arabic, where short function words are built from very common letters, it corrupts constantly.

Fix

Two explicit regexes: one for boundary punctuation, one for a named list of leading filler words. The comment records the reasoning so nobody "simplifies" it back to strip().

How I think about this

The evaluation work is the part I would most want to be asked about.

A judge that certified a hallucination

What happened

My 66-case LLM-as-judge harness scored an answer faithful 1.0 and relevant 1.0, while its own context-recall metric for the same span read 0.0. The answer confidently stated a travel time to the airport that appears nowhere in the retrieved context.

Implication

The judge scored the answer as faithful to a context that did not support it. That single case is the strongest argument in this project for keeping deterministic checks alongside LLM judging.

Consequence

Only 20 of 61 scored cases passed the strict deterministic gate — a far harsher bar than the judge scores, and a healthy corrective to them.

An honest flaw in my own evaluation

The flaw

I ran a controlled model benchmark across 25 scenarios to isolate generation quality from retrieval. The judge_score column came back N/A throughout: the harness supports judge scoring but it was not enabled for that run.

What I do about it

I do not present that benchmark's recommendation as judge-validated. The numbers are still useful for comparing generation behaviour, but the claim they support is narrower than it first appears, and the write-up says so.

What I am not claiming

This working copy is not a git repository, so unlike my other projects I cannot verify commit counts, authorship or an exact date range from history. The only firm date is the audit document's own. Duration and commit-level attribution are left out rather than estimated.

The evaluation figures come from my own harness on my own corpus. They are a regression guard, not a benchmark against anyone else's system.
