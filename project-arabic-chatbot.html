Arabic Advisory Chatbot

A conversational assistant that answers personal questions from a corpus of classical Arabic texts, in Egyptian dialect, by text or by voice. The chat interface was never the hard part. Making retrieval work across a fully diacritized Classical Arabic corpus, when users type undiacritized colloquial Egyptian, was.

What it does

The behaviour that matters here is refusal and fidelity, not fluency. A confident wrong answer about scripture is worse than no answer.

Quotes scripture exactlyQuran and hadith are reproduced verbatim in Classical Arabic and only then explained in dialect. Paraphrasing scripture into dialect is explicitly forbidden.
Admits ignoranceWhen the retrieved passages do not cover the question, it says so plainly instead of producing a fluent, unverifiable answer.
Author and book scoping"What does al-Ghazali say about…" restricts retrieval to that author's work and requires the answer to quote his own wording.
Any language in, same language outBut scripture is never translated. It is quoted in the original and explained in the user's language.
Voice in, voice outA recorded question is transcribed, answered through the same pipeline, and spoken back in a cloned voice.
Accounts, sessions and quotasEmail verification, device fingerprinting, trusted devices, and per-role session and message limits.

See it work

Three behaviours that are hard to get right: quoting a source exactly, scoping to one author, and refusing when the corpus does not cover the question.

Problems I solved

Four that were worth the investigation. In each case the symptom pointed somewhere other than the cause.

A regex that deleted real Arabic letters

Symptom

Queries naming a scholar returned poor results. For a long time this looked exactly like a weak retriever, which is the most common and most misleading diagnosis in RAG work.

Cause

The diacritics-stripping regex used a character range running continuously up to U+06E8. That range spans U+06E5–U+06E6, which are not diacritics — they are real Arabic letters, small waw and small ya. The pattern was deleting base letters. The word الرازي ("al-Razi") normalized to an empty string, so any query naming him produced an empty search and matched nothing.

Fix

Split the range in two with a deliberate gap, verified against Python's unicodedata nonspacing-mark category for the whole U+0600–U+06FF block. The index builder now writes ranges as explicit \uXXXX escapes rather than literal characters, because visually similar Arabic combining marks are near-impossible to proofread when typed directly — that had already produced one silently broken, order-scrambled range.

False "I don't know" answers, traced to how people actually ask

Symptom

The system reported "my sources don't contain this" on questions it could clearly answer.

Analysis

Roughly 56% of real user questions describe the shape of the answer they want, not its topic — "give me a hadith that talks about marriage". The lexical query was built from all content words, so it required hadith and talks about to co-occur with the actual topic. Source chunks never narrate "here is a hadith about…", so the strict match found nothing, fell back to a weak match, and surfaced chunks about the concept of hadith instead of about marriage.

Decision

Strip a curated set of meta-request words, including Egyptian dialect verb forms (بيتكلم, بيتحدث), from the lexical query only. Semantic search keeps the full query, because embeddings tolerate the extra words and stripping them risks shifting vector results. Two words were deliberately left in (قرآن, سورة) because they can legitimately be the topic.

Why it matters

The same word is noise in one search system and signal in the other, so it is handled differently in each. That is the part I would defend in an interview.

An author's name is an identifier, not text to search for

Symptom

"What does al-Razi say about prayer being the ascent of the knower" failed, even though the target passage was correctly indexed.

Cause

The query required the literal word الرازي to appear inside the matched chunk. But a chunk from al-Razi's own book does not repeat his name inline. No chunk satisfied the constraint, so it degraded to a weak match that ranked unrelated books above the correct one.

Fix

When a book or author alias is detected, those tokens scope the SQL query and are simultaneously excluded from the words required to co-occur inside the chunk text. I confirmed live that the target chunk existed and was indexed: the retrieval logic was asking the wrong question.

The hub chunk — a vector-space problem wearing a code costume

Symptom

Questions about a specific large tafsir returned passages from the right book that were unrelated to the question. My first instinct was that the book filter was broken.

Evidence

I tested five questions systematically. The filter was working: logs confirmed retrieval was correctly scoped. The problem was inside the correct book. The decisive finding: the same chunk was the top result for three completely unrelated questions. Its embedding sits near the centre of the semantic space for this corpus, so it becomes a near-default result whenever search finds nothing genuinely strong.

Root cause

Chunking. That tafsir's commentary on a single famous verse spans many pages and was split unevenly, so no chunk cleanly represents it.

Decision

I wrote up four candidate fixes with costs and trade-offs, and changed no code in that pass — the deliverable was the diagnosis. The recommendation was staged: prompt hardening as an immediate defensive measure (acknowledged in the writeup as papering over the retrieval problem), stronger lexical weighting next, and metadata-precise re-chunking as the real long-term fix.

How I think about this

Three principles this project taught me, each paid for with a bug.

Normalization is the foundation everything else stands on

Context

The corpus is fully diacritized Classical Arabic (مِعْرَاجُ). Users type plain undiacritized Egyptian (معراج). Byte for byte these do not match, so lexical search fires essentially never without normalization. The pipeline strips diacritics and tatweel and unifies alef variants on both sides, at index time and at query time.

The risk

The same normalization function is duplicated in the index builder and the query path, with an explicit comment requiring the two to stay identical. If they diverge, retrieval silently degrades rather than erroring. Nothing crashes; answers just get worse. That is the most dangerous class of bug in a retrieval system.

Verified

I checked that SQLite FTS5's remove_diacritics tokenizer option does not handle Arabic tashkeel — it targets Latin-script diacritics — which is why normalization happens before insertion rather than being delegated to the tokenizer.

Things I built, measured, and deleted

Deleted

Keyword-boost retrieval. An exact-word matching layer to catch what embeddings miss. It worked, and it added roughly 78 seconds of latency per request. Reverted two commits later. The capability was rebuilt properly as the disk-backed FTS5 index: same goal, viable implementation.

Narrowed

In-memory BM25. Enabled across nine books, hastily narrowed to one when server RAM ran critically low, then replaced wholesale by FTS5. Three commits, each a smaller claim than the last, ending in a different architecture.

Removed

A Prometheus instrumentation library that raised an error on every request. I tried pinning one version, then downgrading to another; neither worked. The third commit dropped the middleware and mounted the client directly. Two failed version pins are still in the git history, and I would rather leave them visible than tidy them away.

What I am not claiming

The hub-chunk investigation also found a case where the model produced a confident, detailed answer while most retrieved chunks were off-topic — evidence it was drawing on general knowledge rather than the sources. That is the exact failure the whole design exists to prevent, and it was still happening at that point.

The 100-question evaluation set is scored, but it is my own harness on my own corpus, not an external benchmark. Treat it as a regression guard, not proof of quality against anyone else's system.
